1 Context and goal

Seed Selector today joins Product Analyzer and FVA data in the browser — two key spaces reconciled by hand, filters applied after the response arrives. A real Large Farm Grower's volumes break that. The goal: one standalone LFG service (UI + backend) with one query contract, per-grower isolation from day one, and every external system consumed as a scheduled, one-way, inbound feed — never called at request time.

The one rule that holds it together: no user request is ever resolved by calling Cropwise Base, AgInsights or PA live. All data movement is inbound and asynchronous. One precise distinction: the Seed Selector login trigger does not fetch anything in the request path — it only enqueues a zone job (fire-and-forget, at-least-once, can never block or slow login); the fetch itself happens on the worker, exactly like the scheduled batch. So "login-triggered" is a scheduling signal, not a runtime dependency — isolation level 3 (neither data nor query patterns leave at request time) holds by construction.

3 Phase 1 — clean steps (option E)

Standalone LFG service on Seeds infra, silo per grower from day one. Each step is releasable; nothing later reworks anything earlier. Phase 1 is deliberately split into two milestones so it doesn't read (or plan) as one monolith:

Milestone P1-MVP · pilot-ready

Steps 1–7 (epics A–F): foundations, identity, sync, model, Route 1 only, zones, serving contract — enough to run the pilot grower end to end with UI upload. ~95 points.

Milestone P1-PROD · production-hardening

Steps 8–9 (epics G–I): Route 2 only after the pilot validates Route 1's templates (unless a signed business requirement says otherwise), then hardening + pilot sign-off. ~35 points.

  1. Foundations — Terraform: VPC, EKS, RDS, S3, SQS, ECR; two environments (sandbox · production); CI/CD with a manual gate before prod.Exit: a hello-world deploys to sandbox through the pipeline.
  2. Identity & control plane — Cropwise Base JWKS verification; grower registry; memberships (sub → grower, role); tenant guard on X-Grower-Id; silo provisioning automation (DB → user → migrations → secret → registry row).Exit: non-member gets 403; "create grower" produces a working silo.
  3. Master-data sync — scheduled inbound job: Cropwise Base orgs/properties/fields → control plane; canonical field identity established.Exit: a field created in Cropwise Base appears in LFG without manual entry.
  4. Canonical model — farm/field/field_season + metric_definition registry (metrics as rows; country-scoped; seeded with the bgf keys) + catalog-driven migrations across silos.Exit: same migration applied to every silo by one command.
  5. Route 1 ingest — upload → profile → mapping UI → entity worklist (entity_alias) → validation → single commit boundary (batch_id) with per-row rejects and batch rollback.Exit: a real bgf file becomes fact rows; rollback removes exactly its rows.
  6. Zones via AgInsights — SQS lanes (interactive/backfill, DLQ); workers fetch FVA/zones per field; immutable variability_window vintages; batch-per-grower scheduler; Seed Selector login trigger for newly created fields.Exit: login → new field zoned while the session is still open.
  7. Serving contract — the one query API for Seed Selector: join + variability + PD filters at source (fig-4 fan-out as a SELECT).Exit: the UI renders the analysis with zero client-side joins.
  8. Route 2 direct inject — scheduled runner, service identity, template reuse, idempotency by file hash, DLQ; grower-database connector.Exit: a dropped file loads unattended; a re-drop doesn't double-load.
  9. Hardening + pilot — backups (PITR + hourly→daily→monthly) with a restore drill, WAF/rotation/pgAudit, dashboards + alarms, DR tabletop; then the first real grower end to end.Exit: pilot grower's own data answers a fig-4 query in production.

4 Phase 2 — clean steps (option F, deferred)

Reads exactly what Phase 1 built. Deferring costs nothing; retrofitting silos onto a pooled store is the migration nobody wants.

  1. Governance first, no code — cohort threshold, audit policy, export review, sign-off owners. The threshold is a policy decision (set too low, repeated aggregate queries leak). Engineering waits for the signature; the drafting does not wait for Phase 1 — it runs in parallel with P1-PROD.Exit: signed governance doc.
  2. Aggregation gate — the only cross-silo reader: computes above-threshold cohort statistics; minimum cohort enforced in code; every export audited; no row-level egress path exists.Exit: gate refuses any aggregate under the cohort minimum, with an audit row.
  3. Benchmark / model layer — the successful-field benchmark (PD threshold parameterises it); similarity scoring with per-attribute favourable-direction semantics from metric_definition.Exit: benchmark reproducible from gate outputs alone.
  4. Recommendations back into silos — results delivered into each grower's silo; the UI explains verdicts ("matches successful fields on VxC, irrigation…").Exit: a grower sees cohort-informed recommendations with explanations, and raw rows still never crossed.

6 Jira backlog — epics and tickets, in build sequence

Nine phase-1 epics (A–I) + one phase-2 epic (J), strictly ordered; tickets inside an epic can parallelize unless a dependency says otherwise. Points are relative (1 ≈ half a day, 8 ≈ a week). Every ticket inherits the global Definition of Done (§15 of the engineering doc).

7 Anticipated reviewer challenges — with answers

The ten questions a design review should ask, answered in advance. (Several were raised in pre-review and are incorporated above.)

#ChallengeAnswer
1Silo-per-grower is an operational burden — provisioning, migrations, backups, credentials, monitoring across many DBs.Definition first: logical isolation = one PostgreSQL database per grower (own user, KMS key, S3 prefix, backup line); physical = many databases sharing a few pooled Multi-AZ RDS hosts — not instance-per-grower. Target: tens of growers at pilot, low hundreds at scale. Every per-silo operation is a catalog-driven job, never a human task (provisioning LFG-6; migrations with per-silo failure reporting; backup-freshness alarms LFG-24/26). Beyond hundreds: silo tiering behind the same registry — a placement policy, not a redesign. Pooled-then-migrate was rejected as strictly worse. Ops detail: engineering design §10/§17.
2"Everything is scheduled" contradicts the login-triggered AgInsights job.Fixed in §2: login only enqueues (fire-and-forget, at-least-once, idempotency-absorbed); the fetch runs on the worker exactly like the batch. Login-triggered is a scheduling signal, not a runtime dependency — login can never block or slow on it.
32 GB uploads: profiling, validation and rollback need a resource strategy, not just "async".Added to LFG-10/13 scope: streamed parsing (never whole-file in memory; profiling reads the first N MB), chunked validation with bounded worker memory (requests/limits + one file per worker at a time), batch commit in chunked transactions grouped under one batch_id (rollback stays a single DELETE WHERE batch_id), per-stage timeouts, and resume-from-chunk on retry keyed by file hash + offset.
4p95 < 800 ms is asserted against a vague "LFG-sized silo".Benchmark now defined (LFG-20 AC): synthetic silo of 250 fields × 6 seasons × 65 varieties ≈ 100k field_season_metric rows + 1,500 zoning vintages (≈ 20× the 391-row bgf sample), at 20 concurrent requests, PD-threshold changed per request (worst case: benchmark re-selection). This is tractable because zone metrics are pre-computed rows — the query is indexed SQL, not geometry math at request time. Load test is part of the ticket's DoD, with the dataset generator committed.
5What if AgInsights is down for hours or days?Serving never touches AgInsights, so nothing breaks — data goes stale, which the UI must say honestly: every vintage carries its window + computed-at date; the UI shows a freshness badge ("zones as of <date>") and an explicit "zoning pending" state for never-zoned fields — distinct from an error state. Jobs stay queued and drain when AgInsights returns; the backfill scheduler self-heals missed runs; a >24 h feed-staleness alarm pages ops, not the user.
6Master-data sync only says "CB wins" — what about deletes, renames, moves, duplicates?Explicit rules added to LFG-7: delete in CB → soft-delete in LFG (fact rows keep their field reference; field hidden from pickers; orphan report generated — grower data is never cascaded away). Rename → update display name, keep id + aliases. Property move → re-parent, history retained. Duplicate identity → sync flags it to a reconciliation worklist (human decision, like entity aliases). Every sync run emits a diff report; inconsistent states are surfaced, never silently merged.
7Phase 1 is too big to be called one phase (~130 points).Agreed — split in §3 into P1-MVP (pilot-ready, epics A–F, ~95 pts) and P1-PROD (hardening + Route 2 + pilot, ~35 pts). The go/no-go review sits between them; scope cuts land on P1-PROD, never on the isolation or commit-boundary foundations.
8Route 2 may be over-designed before Route 1 is validated.Epic G is now gated: it starts only after the pilot proves the mapping templates on real files — or on a signed business requirement. The primitives Route 2 needs (templates, aliases, commit boundary, idempotency) are all Route 1 deliverables anyway, so deferral costs nothing.
9Noisy neighbours: one giant grower's upload or window roll starves everyone else.Fair-share added to LFG-15: per-grower in-flight caps on both ingest and zone lanes (a grower can occupy at most K workers), the interactive/backfill lane split already protects users from bulk, and queue-age (not just depth) is the alarm metric so starvation is visible. A pathological tenant degrades their own throughput first.
10Phase 2 stalls on governance (cohort threshold is legally/mathematically hard).Two different dependencies, stated explicitly: engineering dependency — no Phase 2 code (LFG-31+) starts before the governance signature; planning dependency — none: the governance workstream (LFG-30) starts during P1-PROD, in parallel, owned outside engineering, so nobody is "waiting for Phase 1 to finish to start the Phase 2 requirement". And a stalled gate blocks nothing — Phase 1 delivers full value per grower without it. the threshold question is framed with established practice (minimum cell size + audited query budget, à la statistical disclosure control) rather than invented from scratch. Code (LFG-31+) waits for signature — that constraint is the feature, not the bug.
Questions we expect at the implementation review (and where the answers will live)
  • RDS connection pooling at N silos — pool-per-silo sizing, LRU cap, PgBouncer threshold → engineering design §4/§17, measured in LFG-20's load test
  • Migration failure recovery — per-silo resume, partial-failure reporting, rollback of a bad migration → LFG-6 runbook
  • Exact SQS/KEDA scaling limits — max in-flight per lane, per-grower caps, scale-to-zero behaviour → LFG-15 config + fault-injection test
  • S3 2 GB processing behaviour — chunk size, memory ceiling, resume keys, observed throughput → LFG-10/13 load test artifacts
  • Security model of the Phase 2 cross-silo credential — the gate's IAM/DB identity, scope, audit — designed in LFG-30/31, reviewed before any code runs
What review already endorsed: silo isolation from day one (instead of pooled-then-migrate), the gate sitting outside the silos as a clean security boundary, governance-before-code for Phase 2, and the unified TypeScript stack. Those are the load-bearing decisions; the ten answers above are the operational envelope around them.
