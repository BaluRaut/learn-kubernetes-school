1 Summary

A standalone LFG platform (UI inside Seed Selector + NestJS backend) for large farm growers. Each LFG gets its own data silo and its own route in Seed Selector — a dynamic encrypted route id (…/g/9f3ac1…), no readable name and no real id in the URL. The LFG uploads its field + variety data through a mapping UI; the platform then runs AgInsights batch jobs to compute FVA / zones per field and stores every historical season window. Varieties are managed as a layer per country / crop / LFG. Cropwise Base provides login and field identity — we store only its reference IDs, never field geometry. LFG admins control who sees what via personas. No data ever crosses between LFGs.

2 Systems & boundaries

1Cropwise Baselogin (JWKS-verified token) + identity for orgs/properties/fields. LFG stores reference IDs only (sysFieldId, orgId) — no field geometry, no mirrored master data.
2LFG (the grower)provides field data with crop variety — file uploads through the mapping UI. Their data, their silo.
3AgInsightsinternal batch job API (no quota/cost constraints) returning FVA + zones per field. Called by our workers on schedule/trigger — never during a user request.
4Seed Selector UIhosts the LFG experience on a dynamic route per LFG — an encrypted opaque id (/g/9f3ac1…), nothing guessable. Renders; never joins.

3 Data model — variety layer, fields, zone windows

The chain is: variety → field → zones/FVA. Varieties are a managed layer per country / crop / LFG; every variety record points at a field (cb_field_ref); every field accumulates zone/FVA results per season window. The reference dataset for the shape is bgf-records.json (fetched and profiled: 391 records, 2023–2026, 6 regions, 65 varieties).

Storage split — confirming your S3 idea

Yes — S3 for zone storage is the right call, and your data already works this way (geometryFile: "fva-zones/<sysFieldId>-2018-2023.json"). The rule: Postgres holds what you filter/sort on (vxc, pafSpread, NDVI percentiles, window dates — small, indexed rows); S3 holds the heavy immutable payloads (zone geometries, full AgInsights responses, raw uploads). Benefits: cheap versioned storage, lifecycle rules = the backup policy, replay-from-raw recovery — and PostGIS stays optional until real spatial queries appear.

Reference data comes from the LFG: season-window definitions per country/crop (delivered by the LFG — today via email, entered through an audited admin screen), the variety layer (purely LFG-provided, no catalogue seeding), and exact field names (the LFG supplies the authoritative name, so CB-ref matching is expected to be exact; the worklist handles the rare mismatch). Window keys in the wild are year-ranges ("2017-2022" … "2021-2026") and the business speaks in date spans ("15 Apr–15 Oct 2026"; "12 Oct–15 Jan 2027" for southern-hemisphere seasons). zone_window therefore stores both: the label for display/compat, and canonical date_start/date_end for querying — cross-hemisphere seasons cost nothing.

4 Upload UI ingest — file → mapping → submit

1UploadLFG user uploads CSV/XLSX (presigned S3 PUT; async processing; streamed parsing, bounded memory).
2Profileheaders + sample rows parsed; types/units inferred.
3Map columnsthe UI shows grower columns → canonical fields; the user maps and can save the mapping as a reusable template.
4Resolveunknown field/variety names → worklist; fixes saved as aliases (map to cb_field_ref / variety layer).
5Submit → validateuser submits for processing; per-row validation against the country/crop metric registry; per-row reject report.
6Committransactional chunk commits under one batch_id; FK-safe rollback as a unit; raw file stays in S3 for replay.
Two intake triggers, one pipeline: the upload UI, plus a scripted ingest — a cron-scheduled script or a manual internal API trigger — that reuses the saved mapping templates and runs the identical validate→commit path under a service identity (LFG-27). A direct connection into the grower's own database is not in scope.

5 Zones / FVA pipeline — after the data lands

  1. Trigger — once field + variety data is committed for an LFG: a batch job per LFG (scheduled) walks its fields; a Seed Selector login also enqueues that LFG's newly added fields (interactive lane). Enqueue-only at request time — the fetch always runs on workers.Idempotency key: (lfg, cb_field_ref, window, method_version).
  2. Call the AgInsights batch API — imagery-derived FVA + zones per field; rate-limited, retried with backoff, responses cached in S3 so retries never re-pay a call.
  3. Store — full response to s3://lfg-<id>/fva-zones/<ref>-<window>.json; indexed metrics (vxc, heterogeneity, consistency, pafSpread, NDVI percentiles, zone_count) into zone_window with label + canonical dates.
  4. Keep 20 years of history — every window computed is retained for 20 years (S3 lifecycle: Glacier-IR after 2 years; nothing deleted before year 20, then reviewed). Values change per season/request → a re-run supersedes, never edits; "what did zoning say then" stays answerable for two decades.
  5. Serve honestly — every window shows its dates + computed-at; "zoning pending" for new fields is distinct from an error; AgInsights downtime = staleness badge, queued jobs drain on recovery.
Same format per crop — the zone/FVA record structure is identical across crops; only values and season windows differ. That is what lets zone_window be one table and the S3 dump one schema — country- and crop-agnostic.

6 Routes, tenancy & personas

Dynamic route per LFG
  • Seed Selector serves each LFG at its own path — a dynamic encrypted route id (…/g/9f3ac1…): no readable string, no real internal id in the URL. The registry maps token ↔ LFG; tokens are rotatable.
  • The token is display routing only: the backend validates (user sub, lfg) membership on every request — a guessed or leaked URL 403s before any handler.
  • Users in two LFGs switch by route; the wrong route is harmless by construction. Branding lives inside the page, not in the URL.
Personas — LFG-managed visibility
  • Each LFG's admin manages its own users and personas: e.g. lfg_admin (everything + user management), agronomist (fields/zones/uploads), analyst (read-only metrics), region-scoped viewer (assigned regions/farms only).
  • A persona = role + data scope (regions, farms, org lines, or field sets — org-level scoping matters because one LFG spans many CB orgs). Enforced server-side in the query layer — scope filters attach to every silo query, never only hidden in the UI.
  • Persona changes are audited and effective ≤60 s (guard cache TTL).
  • Data review is the LFG's job: dataTrust flags and suspect records are reviewed/overridden by the LFG's own admin/agronomist personas, with every override audited.

12 Appendix — the platform in ten real scenarios

One picture of production life, numbered — and each scenario also exists as its own full-size 4K diagram, plus three sequence diagrams (upload & ingest, zone/FVA job, persona-scoped read): see the scenario & sequence gallery. The SVG of this poster zooms forever.

What each number shows
  • 1 · Onboard a new grower — ops creates the LFG (name, countries, CB org refs); one idempotent automation call provisions the silo DB, user, migrations, KMS key, S3 prefix and secret; an encrypted route id is minted; the admin logs in via Cropwise Base and gets the first membership. Minutes, not days.
  • 2 · Two crops, many varieties, one country — the variety layer holds soybean and corn varieties side by side, all scoped BR; field_season_variety links each field to its variety per season; one country's metric rules validate both crops. Adding a variety is an insert, not a deploy.
  • 3 · Two crops, multiple countries — the farm carries the country, so one silo holds BR and US farms; the same metric key (yield) carries different rules per country and the most-specific rule wins. A new country is registry rows + season windows — zero migrations.
  • 4 · Personas — the LFG's own admin assigns role + data scope (regions, farms, org lines, field sets); the query layer appends the scope filter to every silo query, so visibility is enforced in SQL, not hidden in the UI. Audited, effective ≤ 60 s.
  • 5 · Zones stored & fetched — indexed metrics (vxc, pafSpread, NDVI percentiles, window dates) live as zone_window rows in Postgres for fast lists/filters; the heavy geometry dump lives in S3 and is fetched via presigned URL only when a map opens. 20-year history, supersede-never-edit.
  • 6 · Database — many logical grower DBs share pooled Multi-AZ RDS hosts; the control plane keeps registry/personas/templates in its own small DB; one catalog-driven migration job loops every silo with per-silo reporting.
  • 7 · API ⟷ database — every request carries the CB token + encrypted route; the tenant guard 403s non-members before any handler; then a cached, per-LFG pool (max 5 connections) is the only handle the request code receives — a cross-silo query is unwritable.
  • 8 · Rate limits & security — WAF at the edge, per-user + per-LFG throttles (tight on auth), whitelist validation that rejects unknown fields, and an immutable audit log. Each layer assumes the one above it failed.
  • 9 · Encryption — TLS on every hop (ALB → pod → RDS/S3); at rest, a KMS key per LFG for both RDS and S3; per-silo credentials in Secrets Manager, rotated, never in code or images. One leaked key exposes one grower, never all.
  • 10 · DR for one grower — a bad upload rolls back by batch_id; a corrupted silo is restored alone from PITR/hourly backups and repointed in the registry; a lost region rebuilds from IaC + replicated ECR images + replicated S3. RPO ≤ 1 h, silo restore < 1 h — the other growers never notice.
