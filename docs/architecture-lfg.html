🗺️ The architecture in one picture

Everything below in a single numbered view — 4K PNG here, and an infinitely zoomable SVG in the repo.

What each number does
  • 1 · Seed Selector UI — growers and agronomists on one domain, authenticated via Cropwise Base (Seed Selector already uses it for login, orgs, properties, fields and user profiles). All queries and Route 1 uploads start here; the UI holds no join logic (that was RFC figure 1's whole problem).
  • 2 · Direct inject (Route 2) — Excel drops, FMS connections and bulk API pushes on a schedule, running under a service identity. No human in the loop because the saved mapping template answers the human questions in advance (§5).
  • 3 · ALB + WAF — the single public entry point. Every request's X-Grower-Id is membership-checked against the control plane before any handler runs; a non-member gets 403 (§8 security).
  • 4 · LFG service, one shared fleet (EKS) — the same pods serve every grower: API pods (tenant guard + the one query contract), ingest workers (profile → map → resolve → validate → commit), KEDA-scaled zone workers, and CronJobs for backups, the window-roll scheduler and PA/FVA loaders.
  • 5 · Control plane — its own small database holding reference data only: grower registry (region, tier), memberships, mapping templates, the country-scoped metric_definition registry, audit log and zone_jobs status. No grower rows live here — it answers "who are you, which silo is yours", nothing more (§1, §3).
  • 6 · SQS job lanes — ingest lane plus the two zone lanes (interactive / backfill) with DLQ + alarms. Idempotency key (grower, field, window, method_version); staging commits nothing — everything crosses one commit boundary stamped with batch_id (§5, §13).
  • 7 · Per-grower silos — pooled Multi-AZ RDS hosts carrying many single-grower databases, plus dedicated instances for top-tier growers (a registry change, not a migration). Every silo: own DB user, own KMS key, own S3 prefix, own backup line — no query can name two growers (§2 isolation).
  • 8 · The Cropwise ecosystem — three inbound feeds, all scheduled, one-way: Cropwise Base (identity + master data: orgs, properties, fields, profiles, licenses — synced into the control plane), AgInsights (zones / field variability by field — pulled by the zone jobs, §13), and Product Analyzer (variety + performance). Nothing resolves a live request by calling out, so no grower query pattern ever leaves the boundary (isolation level 3).
  • 9 · Phase 2 — the F gate (deferred) — drawn dashed because it does not exist yet: the governed aggregation gate (minimum cohort in code, audited, no row egress) feeding the shared benchmark layer. Governance is signed before any code; until then the only thing crossing this line is nothing (§1).

1 The architecture: E now, F deferred

One contract for the Seed Selector UI, with the join moved server-side (today it runs in the browser — RFC figure 1). The proposal (figure 8) is two phases with no rework between them:

Phase 1 — now: E
  • Standalone LFG data service on Seeds infra — PA / FVA optional, scheduled, one-way, inbound feeds only. Never in the request path.
  • Per-grower silo from day one — own schema, own key, own retention, own backup; a control plane (auth · routing · schema registry) routes by grower_id.
  • Intake: Route 1 (UI upload) first — it produces the mapping templates — then Route 2 (direct inject) reuses them unattended (§5).
  • Settles isolation levels 1–3: storage, compute, transit (§2).
Phase 2 — deferred: F
  • The aggregation gate over the same silos: minimum cohort size enforced in code, no row-level egress, every export audited.
  • Shared benchmark / model layer → the successful-field benchmark of figure 4; recommendations returned into each silo.
  • Governance agreed before any code — the gate's cohort threshold is a policy decision, and set too low it leaks via repeated queries (RFC fig 7's warning).
  • Reads exactly what phase 1 builds — deferring costs nothing; retro-fitting silos onto a pooled store is the migration nobody wants.
The promise, stated precisely: raw grower rows never cross a silo boundary — in either phase. Phase 1 has no cross-silo path at all; phase 2 permits only above-threshold cohort statistics through one narrow, audited gate. "Your data is not mixed" stays literally true.

3 Canonical model (RFC fig 3) — extended for multi-country LFGs

Three clusters on one registry. The RFC's three load-bearing decisions: metrics as rows on metric_definition (kills hardcoded crop-specific maps, makes every metric a WHERE clause), entity_alias (kills the key-mismatch class), and batch_id on every fact row (makes intake reversible).   • Country lives on the farm — a multi-country LFG is one silo whose farms carry different country codes; country on metric_definition scopes which metrics are valid (and how validated) per farm's country.
  • New country = registry rows, not a migration — the whole point of metrics-as-rows extends cleanly: soybean-in-Brazil and soybean-in-India differ only in which definition rows apply.
  • Versioned by season so historical fact rows stay interpretable when a definition's range or unit convention changes.

4 Variability windows — rolling ranges as immutable versions

Zoning is computed over rolling multi-year windows (2017–2022, then 2018–2023, …). In the RFC's model that is variability_window → zone → zone_metric. The engineering rules that keep it trustworthy:

  • A window is a version, not a state: each computed window is inserted whole — variability_window (field, date_start, date_end, source, batch_id) with its zones and zone_metric rows. Re-computation inserts a new window row and marks the old superseded; nothing is edited in place. "What did the zoning say at that time?" always has an answer.
  • Default read = latest complete window; historical windows are one query away, so 2017–2022 vs 2018–2023 compare side by side — a first-class API, since that comparison is exactly what agronomists ask for.
  • Date ranges, not hardcoded 5-year spans (the RFC already stores a date range) — a crop or geography that moves to 3-year windows is data, not a schema change.
  • PD spread and weighted-average PD are zone_metric rows — which is precisely what lets figure 4's fan-out row be selected and filtered at the source instead of assembled in the browser.
  • Geometry hygiene at ingest: valid polygons, within the field boundary, overlap tolerance — bad geometry is a per-row reject (§5), not a surprise on the map. Shapefile/GeoJSON parsing runs in a sandboxed worker (parser CVE history), size-capped.

5 Two intake routes, one pipeline (RFC fig 2)

Route 1: a grower uploads a CSV/XLSX through the UI and maps it once. Route 2: direct inject — an Excel drop, an FMS/database connection or a bulk API push on a schedule, no human in the loop. They differ only in where they enter: Route 2 reuses the saved mapping template and starts at entity resolution. From validation down, the path and the commit boundary are identical.

The real payload shape — the grower's variety-performance records (see bgf-records.json): per field-year-variety rows carrying yieldPerAc, tuberScore, returnPerAc, pdYield / pdTuber / pdReturn, vxc, heterogeneity, consistency, irrigation/water/power attributes, area and abandonment. Every one of these becomes a metric_definition row (§3) and lands as fact rows — uploaded via the UI (Route 1) or pushed straight from the grower's own database (Route 2).
1UploadFile stored (per-silo S3 prefix); one ingest_batch row created. Route 2 enters here on a schedule with a service identity.
2ProfileHeaders parsed, first N rows sampled, types + units inferred.
3Map columnsGrower columns → canonical fields; template pre-fills matches. Route 2 skips the human step — the template supplies the column + unit map.
4Resolve entitiesUnknown field/variety names → worklist; each fix saved as entity_alias, so keys agree across routes forever after.
5ValidateRequired, units, duplicates, ranges (from metric_definition — country-aware, §3), geometry checks. Errors are per row.
6Save templateColumn map + unit map stored per grower — step 6 is what makes Route 2 possible.
7CommitThe ONLY write to canonical tables. Every fact row stamped batch_id; a batch rolls back as a unit.
Why Route 1 first
  • It is the only route that can resolve new unknown names — because it can ask. Needed to cold-start a grower, a crop or a geography.
  • Steps 3 + 6 produce the mapping template — the template is the entire prerequisite for an unattended feed.
  • Route 2 then survives an LFG's real volumes and cadence; unresolvable names queue to the same worklist instead of blocking the batch.
The commit boundary discipline
  • Staging commits nothing: a scheduled inject that fails validation leaves zero rows in canonical tables.
  • Provenance: every fact row → batch_id → file hash, route, template version, actor. Audits answered in one join.
  • Idempotency: file hash + template version dedupe re-pushed files — an inject retry updates its batch instead of double-loading.
  • Async by construction: big shapefiles process on a queue; the UI polls the batch row — nobody holds an HTTP request open for 2 GB.

6 What the data is for (RFC fig 4) — and what that demands

The performance prediction model compares a live field profile against a benchmark built from historical fields that cleared the user's own Productivity-Difference threshold and had favourable same-year performance. Engineering consequences:

  • The threshold parameterises the benchmark, not the view — changing it re-selects which historical fields count as successful. That is a query over the whole historical set per request, not a filter over a fetched page — exactly the load figure 1's in-browser join can't carry, and the reason the join must live server-side with metrics filterable in SQL.
  • Zone-level metrics must be rows (PD spread, weighted-average PD) so the fan-out is a SELECT, not client-side assembly (§4).
  • Phase 1 scope: the model runs within one silo (a grower benchmarked against their own history). The cross-grower cohort benchmark is exactly the phase-2 F-gate feature — deferred until governance exists (§1).
  • Explainability is a data requirement: "falls below successful benchmarks on drainage score and CEC" needs normalised attributes with per-attribute favourable-direction semantics (higher-is-better / band / categorical similarity) — these semantics belong on metric_definition, not in UI code.

7 Multiple countries: regions, residency, latency

Placement rules
  • Default: one silo per grower in the grower's home region; the control plane's registry records placement and the API routes by it — invisible to clients.
  • Residency exception: where law or contract requires in-country data, split that grower into per-country silos; the API may fan out within one grower's own silos — the no-cross rule is about different growers, not about one grower's countries.
  • Reference data is global: metric_definition and crop/variety catalogues replicate everywhere (no grower data in them).
Practical notes
  • Ingest is latency-tolerant (async); silo placement matters most for dashboard reads — add serving regions only when usage justifies.
  • Units/locales come from metric_definition + farm country (kg/ha vs sacas/ha) — never guessed from the browser.
  • Start single-region with the registry's region column populated — multi-region becomes an operation, not a redesign.

8 Ops: backup, DR, security — inherited patterns

Same shape as the school platform design, re-scoped per grower silo:

  • Backups per silo: PITR + hourly (10 d) → daily (30 d) → monthly (12 mo); monthly restore drills on one random silo. Raw upload files in S3 are versioned — replaying the ingest pipeline from raw is a second, independent recovery path, and batch_id makes the replay verifiable.
  • DR: three replicated pillars (IaC in git, images via ECR replication, data via cross-region S3) + region runbook; RPO ≤ 1 h, region RTO < 4 h.
  • Security: external IdP (identity only) + membership table + per-request tenant check (X-Grower-Id validated every request); DB in private subnets; KMS per silo; Secrets Manager rotation; immutable audit log; WAF; sandboxed geometry parsing (§4).

9 The RFC's open questions — engineering answers in progress

Q4 · Seeds computes performance independently of PA — what if they disagree?
  • A join problem becoming a credibility problem is fair — mitigate with provenance, not authority: every computed metric row carries its source and method version, and the UI can show both values labelled when they differ.
  • Add a scheduled reconciliation report (same inbound-feed machinery) that quantifies divergence per metric — so the discussion is about a number, not a feeling.
Q7 · E is affordable at tens of growers, untenable at thousands
  • The cost driver is silo operations, not storage — so automate them away: catalog-driven migrations, shared app fleet, pooled Postgres instances hosting many single-grower databases (the school platform's exact pattern), PgBouncer as pools multiply.
  • That carries E to hundreds of growers on a handful of instances. At thousands: tier the silos (dedicated instance / shared instance / schema-level) behind the same control plane — routing already abstracts placement, so tiering is a placement policy, not a redesign.

13 Zone-data job queue — how field zoning gets computed

Deriving a field's variability zones (imagery + soil/terrain context → zone geometries + zone_metric rows) is slow, bursty, and depends on rate-limited external APIs — the definition of work that must never run inside an HTTP request. It runs as an asynchronous job queue on SQS, with worker pods on EKS.

1EnqueueTriggers: the scheduled batch per grower · a Seed Selector login enqueues that grower's newly created fields (interactive lane) · a manual re-run. Message = (grower, field, window, method_version) — the idempotency key.
2Fetch from AgInsightsZones / field variability by field come from AgInsights (FVA), not raw imagery. Rate-limited per token bucket; responses cached in S3 so a retry never re-pays the call.
3Compute zonesWorker pod derives zone geometries + per-zone metrics (PD, PAF) for the window. CPU-heavy; workers scale on queue depth (KEDA/HPA), not on HTTP traffic.
4ValidateSame gates as ingest: valid polygons, within field boundary, metric ranges from metric_definition. Failures → job error state, not partial data.
5CommitOne transaction: new variability_window version + zones + zone_metric rows, stamped batch_id. Previous version superseded, never edited (§4).
6Fail wellVisibility timeout + max-receive → DLQ + alarm. DLQ messages carry the last error; re-drive is one command after the cause is fixed.
Queue design
  • Two lanes: an interactive queue (a user asked — minutes matter) and a backfill queue (annual window roll across every field — hours are fine). Separate SQS queues, weighted workers — bulk never starves a waiting user.
  • Idempotent by key: re-delivery or a double-enqueue of (field, window, method_version) short-circuits if that version already committed — at-least-once delivery becomes exactly-once effect.
  • Job status is data: a zone_jobs row per message (queued → fetching → computing → validating → committed | failed) — the UI polls it, dashboards aggregate it.
  • Silo discipline holds: a worker processes one grower's job with that silo's credentials only — the queue carries references, never row data.
Batch per grower + login triggers
  • Scheduled batch per grower (EventBridge cron): walk that grower's fields, enqueue any missing/next window (e.g. 2019–2024 once 2024 closes) on the backfill lane, throttled.
  • Login-triggered: when a user logs into Seed Selector, an event enqueues zone jobs for that grower's newly created fields on the interactive lane — fresh fields get zones while the user is still in the session, without waiting for the nightly batch.
  • New method version (algorithm change) = optional re-enqueue of recent windows with the new method_version — old vintages stay, comparisons stay honest.
  • Progress is observable per grower: "fields zoned for window W: 1,240 / 1,300, 4 failed" — from the zone_jobs table, no log-diving.

15 Definition of Done

A milestone (or any ticket inside one) is Done only when every line below holds. "Works on my machine" and "merged" are not states in this list.

Code & correctness
  • Reviewed and merged; unit + integration tests pass in CI (integration = real Postgres/PostGIS, not mocks, for anything touching the silo).
  • Migrations applied across all sandbox silos by the catalog job — not by hand.
  • Idempotency and rollback demonstrated where applicable (re-run a batch, re-deliver a message — no double data).
  • Tenant isolation asserted by a test: a request with grower A's identity against grower B's resource returns 403 and touches no silo.
Operable & observable
  • Dashboards + alarms exist for the new path (error rate, queue depth, latency) — shipped with the feature, not after.
  • Runbook entry written: what alarms mean, how to re-drive, how to roll back.
  • Provenance verifiable: any committed row traces to batch_id → run → file/job → actor in one query.
  • Cost tagged: new resources carry the tagging standard so Cost Explorer attributes them.
  • Load-checked at representative volume (an LFG-sized file / a full-grower window roll), not toy data.
  • Demoed in sandbox with real-shaped data; this design doc updated if behaviour diverged from it.

17 Infrastructure choices — compared, decided, with revisit triggers

Every layer had real alternatives. This table records what was considered, what we use, why for this workload (bursty geospatial jobs, many small Postgres databases, modest request traffic at first), and — most importantly — the concrete trigger that would reopen the decision. A decision without a revisit trigger is dogma.

LayerOptions consideredDecisionWhy — and when to revisit
Container orchestration EKS · ECS Fargate · Lambda-only · plain EC2 EKS CronJobs, KEDA queue-scaling, and the worker patterns in §13 map 1:1 to Kubernetes; skills and IaC already exist. Honest note: ECS Fargate is operationally simpler for a very small team — EKS wins here on job orchestration + existing investment, not on simplicity. Revisit: if cluster upkeep ever consumes >10% of team time, trial ECS/Fargate for the API tier.
Relational database RDS PostgreSQL · Aurora PostgreSQL · self-managed on EC2 · DynamoDB RDS PostgreSQL + PostGIS PostGIS is non-negotiable (kills DynamoDB); self-managed loses Multi-AZ/PITR for no gain. Vs Aurora: RDS is ~20–30% cheaper per instance for steady small-DB workloads, and the pooled many-databases-per-host pattern needs no Aurora features. Revisit: a pooled host passing ~1 TB or needing read replicas per grower → move that host to Aurora (same engine, low-drama migration).
Job queue SQS · Kafka (MSK) · RabbitMQ (AmazonMQ) · Postgres-based queue SQS (+ DLQ) We need work distribution with retries and DLQ, not stream replay or ordering — SQS gives that serverless at ~zero cost and zero ops. MSK is a cluster to babysit; a Postgres queue couples job load to silo hosts. Revisit: if multiple independent consumers ever need to replay the same event history (true event streaming), introduce MSK alongside SQS — not instead of.
Zone-compute workers EKS worker pods (KEDA) · AWS Batch · Lambda EKS pods, KEDA-scaled Zone jobs are CPU-heavy and can exceed Lambda's 15-min cap on large fields; Batch works but adds a second orchestrator for jobs the cluster can already run. Scale-to-zero via KEDA keeps idle cost near nil. Revisit: if compute needs GPUs or 10×-spiky scientific workloads, AWS Batch (or Karpenter spot pools) earns its place.
API edge ALB · API Gateway · CloudFront + ALB ALB (+ WAF) Steady authenticated app traffic → ALB is cheaper at volume and WAF attaches directly; API Gateway's per-request pricing and 29 s timeout buy features we don't need (usage plans, API keys). Revisit: when the partner-facing bulk API (Route 2) gets external consumers, front just that with API Gateway for keys/quotas; add CloudFront when a browser UI ships heavy static assets.
Infrastructure as code Terraform · CDK · CloudFormation · Pulumi Terraform Existing codebase and team fluency; the module ecosystem (VPC/EKS/RDS) is the most worn path; state + plan reviews fit the CI gate. CDK is attractive for TypeScript teams but adds a synth layer to debug. Revisit: only with a platform-team decision — mixed IaC is worse than either choice.
CI/CD CircleCI · CodePipeline/CodeBuild · GitHub Actions CircleCI Already wired (AWS context, ECR push, EKS deploy, manual gate) — the stages are identical on any runner, so this is the lowest-switching-cost decision on the page. Revisit: if an AWS-only mandate hardens, CodePipeline is a mechanical port; if the org consolidates on GitHub, Actions likewise.
Secrets & config Secrets Manager · SSM Parameter Store · Vault Secrets Manager + Parameter Store Split by nature: Secrets Manager for per-silo DB credentials (rotation is the feature — $0.40/secret is the price of it); free-tier Parameter Store for non-secret config. Vault is real power at real ops cost — unjustified at this scale. Revisit: multi-cloud or dynamic short-lived DB creds per request → Vault.
Observability CloudWatch + Container Insights · Prometheus/Grafana (AMP/AMG) · Datadog CloudWatch first AWS-only constraint, zero extra infrastructure, alarms + dashboards good enough for the §16 cadence. Prometheus is the better k8s-native fit eventually; Datadog is the best product at the worst price. Revisit: when engineers routinely need high-cardinality per-grower metrics (per-silo latency histograms), adopt AMP/AMG managed Prometheus — keep CloudWatch for AWS-service alarms.
Geometry processing In-DB PostGIS · dedicated geo service · GeoPandas workers PostGIS for storage/query · workers for parsing Split by trust boundary: untrusted file parsing (shapefile/GeoJSON) happens in sandboxed worker pods (§4's CVE note); validated geometries then live in PostGIS where window queries and joins are SQL. One database fewer, one attack surface contained. Revisit: raster/imagery analysis at scale → dedicated workers with rasterio, results still landing in PostGIS.
The meta-decision: every choice above favors managed, boring, already-known over optimal-on-paper — because the team's scarce resource is operational attention, and §16's cadence is only sustainable if the infrastructure mostly runs itself. The revisit triggers are the honesty mechanism: each one names the measurable moment where "boring" stops being the right answer.
