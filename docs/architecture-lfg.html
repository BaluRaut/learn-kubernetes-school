🌾 LFG Platform — Multi-Country Grower Architecture

The design for serving Large Farm Growers that operate across countries — with country-specific crop attributes, rolling field-zoning windows (2017–2022, 2018–2023, …), dual data ingestion (Upload UI / CI job) through a schema-mapping layer, and a hard rule: no data ever crosses between LFGs.

1 Silo per LFG — and deliberately no aggregate gate

Same skeleton as the school platform's option E: a small control plane (LFG registry, memberships, mapping templates, feature flags) and one database silo per LFG. One difference is a decision, not an omission:

No option F here. The requirement is "no data share cross LFG" — so this platform has no aggregation gate at all. There is no service, job, credential or path that reads two silos. Cross-LFG benchmarking, if ever requested, would be a new signed agreement and a new design — not a toggle.
What's in a silo (per LFG)
  • Growers' org data: farms, fields, seasons, crops, observations, zoning vintages.
  • Its own DB credentials, its own KMS key, its own S3 prefixes (raw uploads + backups).
  • Its own mapping templates and ingest history — even the shape of an LFG's source files is treated as confidential.
What's in the control plane
  • LFG registry: silo location (region!), status, plan.
  • Memberships: IdP sub → LFG + role (same external-auth pattern as the school doc: token = WHO, membership table = MAY/AS WHAT, X-Lfg-Id header = WHICH, checked every request).
  • Country attribute dictionaries (§2) — platform-owned reference data, not grower data.

2 Multi-country LFGs & per-country crop attributes

An LFG can farm in Brazil, India and Ukraine at once. The core entities are identical everywhere (farm → field → season), but what you measure about a crop differs by country — soybean in Brazil carries different attributes than soybean in India (regulatory, agronomic, unit conventions). Hard-coding columns per country would mean a migration for every new market. Instead: an attribute dictionary.

The dictionary (platform reference data) 
crop_attribute_defs
  country        "BR" | "IN" | "UA"
  crop           "soybean" | "wheat" | ...
  attr_key       "maturity_group" | "protein_pct" | ...
  value_type     number | text | enum | date | boolean
  unit           "kg/ha" | "%" | null
  enum_values    [...]           -- when value_type = enum
  rules          { min, max, required, regex }
  since_season   2023            -- dictionary is versioned too
Adding a country or a new attribute = inserting dictionary rows, not a schema migration. The dictionary is versioned by season so historical data stays interpretable.
The data (in each silo) 
season_crop_data
  field_id       → fields
  season_year    2024
  crop           "soybean"
  country        "BR"            -- denormalized for validation
  attrs          JSONB           -- ONLY keys allowed by the
                                 -- (country, crop) dictionary
-- GIN index on attrs for querying
-- CHECK: validated at API + ingest, not by trigger
  • Validation at the edges: API writes and the ingest pipeline both validate attrs against the dictionary — wrong type, unknown key, out-of-range → rejected with a precise error.
  • Typed reads: the API serves attributes together with their definitions (type, unit, label) so every UI renders any country's crops without country-specific code.

3 Field zoning — rolling year-windows as immutable vintages

Each field carries zoning computed over a rolling multi-year window: 2017–2022, then 2018–2023, and so on. Each window's result is a vintage — stored whole, never edited, never overwritten by the next window.

field_zoning_vintages
  id
  field_id        → fields
  window_start    2018
  window_end      2023                  -- UNIQUE (field_id, window_start, window_end)
  zones           GEOMETRY(MultiPolygon, 4326)   -- PostGIS; one row per zone alternative:
  zone_props      JSONB                 -- per-zone class/productivity attributes
  source          "upload" | "ci:pipeline-name"
  ingest_run_id   → ingest_runs        -- full provenance
  created_at      timestamptz          -- immutable after insert
  • Default read = latest complete window (ORDER BY window_end DESC LIMIT 1); any historical window stays one query away — agronomists can compare 2017–2022 vs 2018–2023 zoning side by side.
  • Immutability: a re-computation of the same window inserts a new vintage row (with new ingest_run_id) and marks the old one superseded — you can always answer "what did the zoning say at that time?"
  • Window length is data, not code: storing start + end (not "the 5-year window") means a country or LFG that moves to 3-year windows needs zero schema change.
  • Geometry hygiene: zones validated on ingest (valid polygons, within the field boundary, no overlaps beyond tolerance) — bad geometry is a reject, not a surprise on the map later.

4 The data model in one view

CONTROL PLANE (one, global)                 SILO (one per LFG)
─────────────────────────────               ─────────────────────────────
lfg_registry    (silo region, status)       farms          (country per farm!)
memberships     (idp_sub → lfg, role)       fields         (farm_id, boundary GEOMETRY)
crop_attribute_defs (country, crop, ...)    seasons        (year, crop per field)
mapping_templates   (per lfg+country)       season_crop_data (attrs JSONB, §2)
ingest_runs registry (status only)          field_zoning_vintages (§3)
audit_log                                   ingest_runs / reject_rows (detail)
                                            uploads_raw pointer → s3://lfg-/raw/
  • Country lives on the farm, not the LFG — a multi-country LFG is just farms with different country codes, and each farm's crops validate against that country's dictionary.
  • Mapping templates sit in the control plane but are scoped per LFG — they contain no grower data, only column-mapping recipes; still, they're never listed across LFGs.

5 Ingestion: Upload UI and CI job → one pipeline

Two doors, one hallway. Whether an agronomist drags a CSV into the browser or a nightly CI job pushes a partner export, the file takes the same validated path — so there is exactly one place where mapping, validation and provenance are enforced.

1ArriveUpload UI (presigned S3 PUT) or CI job (service token from the CI context — machine identity, same membership check). Lands in s3://lfg-<id>/raw/<run>/.
2Register runingest_runs row: who/what, LFG, file hash, source=upload|ci. Everything downstream links to this run.
3MapA mapping template (per LFG + country + source type) translates source columns → target fields/attr keys, with unit conversions and transforms.
4ValidateRows checked against the country dictionary (§2) + geometry checks for zoning files (§3). Row-level verdicts.
5LoadValid rows upserted into the LFG's silo in one transaction per batch; zoning becomes a new vintage.
6ReportReject report per run: row, column, reason ("attr protein_pct > max 60", "polygon self-intersects"). Downloadable; nothing silently dropped.
Mapping template (stored, reusable, versioned) 
mapping_templates
  lfg_id, country, source_kind   "csv" | "geojson" | "shapefile" | "api"
  version                        7      -- runs record which version they used
  map:
    "Talhao"        → field.external_ref
    "Cultura"       → season.crop        (values: {"Soja":"soybean", ...})
    "Prod_sc_ha"    → attrs.yield        (unit: sc/ha → kg/ha, ×60)
    "ZonaGeo"       → zoning.zones       (geojson, srid 4674 → 4326)
  defaults: { season_year: from filename /(\d{4})/ }
Why one pipeline matters
  • The UI is just a client of the same ingest API the CI job calls — no "the upload path validates but the CI path doesn't" drift, ever.
  • Idempotency: file hash + template version dedupe re-runs; a re-pushed CI file updates its run instead of double-loading.
  • Provenance answers audits: every row and every zoning vintage points to its ingest run → file → uploader/pipeline → mapping version.
  • Big files: processing is an async job (queue) with progress on the run row — the UI polls the run, nobody holds an HTTP request open for a 2 GB shapefile.

6 "No data share cross LFG" — made structural

  • Database: silo per LFG with per-LFG credentials — a connection for LFG A cannot express a query touching LFG B. No shared tables containing two LFGs' rows anywhere.
  • Object storage: s3://lfg-<id>/… prefixes with IAM policies scoped per prefix; presigned URLs are minted per LFG per request.
  • API: X-Lfg-Id membership-checked on every request (external-IdP pattern); resources embed their LFG and the tenant guard compares — a leaked ID in a URL still 403s.
  • No aggregate path: no cross-silo job, no benchmark service, no "platform analytics" credential. The platform team's operational role can see metadata (run counts, sizes, health) — never row data.
  • Backups & keys: per-LFG backup lines and per-LFG KMS keys — even at rest, LFGs don't share a blast radius.
  • Egress review: the only data that leaves a silo is what that LFG's own users export, and exports are audited (who, what, when, how many rows).

7 Multiple countries: regions, residency, latency

Placement rules
  • Default: one silo per LFG, placed in the LFG's home region (catalog records it; the API routes by catalog, so placement is invisible to clients).
  • Residency exception: where law requires in-country data (or the LFG's contracts do), split that LFG into per-country silos — the LFG's own users see a unified view because the API fans out within one LFG's own silos only.Fan-out inside one tenant is fine; the no-cross rule is about different LFGs.
  • Reference data is global: attribute dictionaries replicate to every region (they contain no grower data).
Practical notes
  • Field-level geometry work (zoning uploads) is latency-tolerant (async pipeline) — silo placement matters more for dashboard reads; keep the app fleet in each serving region behind latency-based DNS if usage justifies it.
  • Units and locales come from the dictionary + country (metric vs sacas/ha etc.) — never guessed from the browser.
  • Start with one region + the catalog's region column populated — multi-region becomes an operation, not a redesign.

8 Ops: backup, DR, security — inherited patterns

These are identical in shape to the school platform design, re-scoped per LFG. Differences only:

  • Backups per LFG (not per school): PITR + hourly (10 d) → daily (30 d) → monthly (12 mo); restore drills pick one random LFG monthly. Raw upload files in S3 are themselves versioned — the ingest pipeline can be replayed from raw, which is a second, independent recovery path for derived data.
  • DR: same three replicated pillars (IaC in git, images in ECR replication, data in cross-region S3) + the same region runbook; RPO ≤ 1 h, region RTO < 4 h. Multi-region silos (§7) already halve the blast radius.
  • Security: external IdP (identity only) + membership table + per-request tenant check; DB in private subnets, KMS per LFG, Secrets Manager rotation, immutable audit log, WAF. Plus one LFG-specific rule: geometry files are treated as untrusted input — parsed in a sandboxed worker (shapefile/GeoJSON parsers have CVE history), size-capped, and validated before anything touches the silo.

9 Build order

  • 1. Control plane: LFG registry (+region), memberships on the IdP's sub, tenant guard with X-Lfg-Id.
  • 2. Core silo schema: farms (with country) → fields (boundary) → seasons; migrations loop over the catalog.
  • 3. Attribute dictionary + validated JSONB writes for one country/crop pair, then add countries as dictionary rows.
  • 4. Ingest pipeline v1: ingest_runs + CSV mapping templates + reject reports — Upload UI first (it forces the API shape), CI job second (same API, service token).
  • 5. Zoning vintages: PostGIS, GeoJSON ingest, window queries, side-by-side vintage compare API.
  • 6. Backups + first restore drill (one LFG), then security hardening pass (WAF, rotation, sandboxed geometry parsing).
  • 7. Residency work only when the first contract demands it — the catalog's region column is already waiting.
Reuse note: control plane, tenant guard, membership model, backup jobs and the DR runbook are the same components as the school platform — two products, one platform skeleton. Build them once, parameterize the tenant type.
