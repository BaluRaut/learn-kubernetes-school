1 Options A–F, and the chosen phasing

The RFC's figure 5 lays out six options that all give the Seed Selector UI one contract and move the join server-side (today it runs in the browser — figure 1). The proposal (figure 8) is two phases with no rework between them:

Phase 1 — now: D + E
  • Standalone LFG data service on Seeds infra — PA / FVA optional, scheduled, one-way, inbound feeds only. Never in the request path.
  • Per-grower silo from day one — own schema, own key, own retention, own backup; a control plane (auth · routing · schema registry) routes by grower_id.
  • Intake: Route 1 (UI upload) first — it produces the mapping templates — then Route 2 (direct inject) reuses them unattended (§5).
  • Settles isolation levels 1–3: storage, compute, transit (§2).
Phase 2 — deferred: F
  • The aggregation gate over the same silos: minimum cohort size enforced in code, no row-level egress, every export audited.
  • Shared benchmark / model layer → the successful-field benchmark of figure 4; recommendations returned into each silo.
  • Governance agreed before any code — the gate's cohort threshold is a policy decision, and set too low it leaks via repeated queries (RFC fig 7's warning).
  • Reads exactly what phase 1 builds — deferring costs nothing; retro-fitting silos onto a pooled store is the migration nobody wants.
The promise, stated precisely: raw grower rows never cross a silo boundary — in either phase. Phase 1 has no cross-silo path at all; phase 2 permits only above-threshold cohort statistics through one narrow, audited gate. "Your data is not mixed" stays literally true.

3 Canonical model (RFC fig 3) — extended for multi-country LFGs

Three clusters on one registry. The RFC's three load-bearing decisions: metrics as rows on metric_definition (kills hardcoded crop-specific maps, makes every metric a WHERE clause), entity_alias (kills the key-mismatch class), and batch_id on every fact row (makes intake reversible). One extension is needed for growers operating across countries:

The multi-country extension

  • Country lives on the farm — a multi-country LFG is one silo whose farms carry different country codes; country on metric_definition scopes which metrics are valid (and how validated) per farm's country.
  • New country = registry rows, not a migration — the whole point of metrics-as-rows extends cleanly: soybean-in-Brazil and soybean-in-India differ only in which definition rows apply.
  • Versioned by season so historical fact rows stay interpretable when a definition's range or unit convention changes.

4 Variability windows — rolling ranges as immutable versions

Zoning is computed over rolling multi-year windows (2017–2022, then 2018–2023, …). In the RFC's model that is variability_window → zone → zone_metric. The engineering rules that keep it trustworthy:

  • A window is a version, not a state: each computed window is inserted whole — variability_window (field, date_start, date_end, source, batch_id) with its zones and zone_metric rows. Re-computation inserts a new window row and marks the old superseded; nothing is edited in place. "What did the zoning say at that time?" always has an answer.
  • Default read = latest complete window; historical windows are one query away, so 2017–2022 vs 2018–2023 compare side by side — a first-class API, since that comparison is exactly what agronomists ask for.
  • Date ranges, not hardcoded 5-year spans (the RFC already stores a date range) — a crop or geography that moves to 3-year windows is data, not a schema change.
  • PD spread and weighted-average PD are zone_metric rows — which is precisely what lets figure 4's fan-out row be selected and filtered at the source instead of assembled in the browser.
  • Geometry hygiene at ingest: valid polygons, within the field boundary, overlap tolerance — bad geometry is a per-row reject (§5), not a surprise on the map. Shapefile/GeoJSON parsing runs in a sandboxed worker (parser CVE history), size-capped.

5 Two intake routes, one pipeline (RFC fig 2)

Route 1: a grower uploads a CSV/XLSX through the UI and maps it once. Route 2: direct inject — an Excel drop, an FMS connection or a bulk API push on a schedule, no human in the loop. They differ only in where they enter: Route 2 reuses the saved mapping template and starts at entity resolution. From validation down, the path and the commit boundary are identical.

1UploadFile stored (per-silo S3 prefix); one ingest_batch row created. Route 2 enters here on a schedule with a service identity.
2ProfileHeaders parsed, first N rows sampled, types + units inferred.
3Map columnsGrower columns → canonical fields; template pre-fills matches. Route 2 skips the human step — the template supplies the column + unit map.
4Resolve entitiesUnknown field/variety names → worklist; each fix saved as entity_alias, so keys agree across routes forever after.
5ValidateRequired, units, duplicates, ranges (from metric_definition — country-aware, §3), geometry checks. Errors are per row.
6Save templateColumn map + unit map stored per grower — step 6 is what makes Route 2 possible.
7CommitThe ONLY write to canonical tables. Every fact row stamped batch_id; a batch rolls back as a unit.
Why Route 1 first
  • It is the only route that can resolve new unknown names — because it can ask. Needed to cold-start a grower, a crop or a geography.
  • Steps 3 + 6 produce the mapping template — the template is the entire prerequisite for an unattended feed.
  • Route 2 then survives an LFG's real volumes and cadence; unresolvable names queue to the same worklist instead of blocking the batch.
The commit boundary discipline
  • Staging commits nothing: a scheduled inject that fails validation leaves zero rows in canonical tables.
  • Provenance: every fact row → batch_id → file hash, route, template version, actor. Audits answered in one join.
  • Idempotency: file hash + template version dedupe re-pushed files — an inject retry updates its batch instead of double-loading.
  • Async by construction: big shapefiles process on a queue; the UI polls the batch row — nobody holds an HTTP request open for 2 GB.

6 What the data is for (RFC fig 4) — and what that demands

The performance prediction model compares a live field profile against a benchmark built from historical fields that cleared the user's own Productivity-Difference threshold and had favourable same-year performance. Engineering consequences:

  • The threshold parameterises the benchmark, not the view — changing it re-selects which historical fields count as successful. That is a query over the whole historical set per request, not a filter over a fetched page — exactly the load figure 1's in-browser join can't carry, and the reason the join must live server-side with metrics filterable in SQL.
  • Zone-level metrics must be rows (PD spread, weighted-average PD) so the fan-out is a SELECT, not client-side assembly (§4).
  • Phase 1 scope: the model runs within one silo (a grower benchmarked against their own history). The cross-grower cohort benchmark is exactly the phase-2 F-gate feature — deferred until governance exists (§1).
  • Explainability is a data requirement: "falls below successful benchmarks on drainage score and CEC" needs normalised attributes with per-attribute favourable-direction semantics (higher-is-better / band / categorical similarity) — these semantics belong on metric_definition, not in UI code.

7 Multiple countries: regions, residency, latency

Placement rules
  • Default: one silo per grower in the grower's home region; the control plane's registry records placement and the API routes by it — invisible to clients.
  • Residency exception: where law or contract requires in-country data, split that grower into per-country silos; the API may fan out within one grower's own silos — the no-cross rule is about different growers, not about one grower's countries.
  • Reference data is global: metric_definition and crop/variety catalogues replicate everywhere (no grower data in them).
Practical notes
  • Ingest is latency-tolerant (async); silo placement matters most for dashboard reads — add serving regions only when usage justifies.
  • Units/locales come from metric_definition + farm country (kg/ha vs sacas/ha) — never guessed from the browser.
  • Start single-region with the registry's region column populated — multi-region becomes an operation, not a redesign.

8 Ops: backup, DR, security — inherited patterns

Same shape as the school platform design, re-scoped per grower silo:

  • Backups per silo: PITR + hourly (10 d) → daily (30 d) → monthly (12 mo); monthly restore drills on one random silo. Raw upload files in S3 are versioned — replaying the ingest pipeline from raw is a second, independent recovery path, and batch_id makes the replay verifiable.
  • DR: three replicated pillars (IaC in git, images via ECR replication, data via cross-region S3) + region runbook; RPO ≤ 1 h, region RTO < 4 h.
  • Security: external IdP (identity only) + membership table + per-request tenant check (X-Grower-Id validated every request); DB in private subnets; KMS per silo; Secrets Manager rotation; immutable audit log; WAF; sandboxed geometry parsing (§4).

9 The RFC's open questions — engineering answers in progress

Q4 · Seeds computes performance independently of PA — what if they disagree?
  • A join problem becoming a credibility problem is fair — mitigate with provenance, not authority: every computed metric row carries its source and method version, and the UI can show both values labelled when they differ.
  • Add a scheduled reconciliation report (same inbound-feed machinery) that quantifies divergence per metric — so the discussion is about a number, not a feeling.
Q7 · E is affordable at tens of growers, untenable at thousands
  • The cost driver is silo operations, not storage — so automate them away: catalog-driven migrations, shared app fleet, pooled Postgres instances hosting many single-grower databases (the school platform's exact pattern), PgBouncer as pools multiply.
  • That carries E to hundreds of growers on a handful of instances. At thousands: tier the silos (dedicated instance / shared instance / schema-level) behind the same control plane — routing already abstracts placement, so tiering is a placement policy, not a redesign.
