FIG 1

The join runs in the browser

Two services, keyed independently. Steps 1 and 2 are server-side jobs with no server to run on, so they run in the client — which is why the result set is never narrowed at the source.

FIG 2

Two intake routes, one pipeline

Both options on the table. Route 1 is a grower uploading a file through the UI and mapping it once. Route 2 is direct inject — an Excel drop, an FMS connection or a bulk API push, running on a schedule with no human in the loop. They differ only in where they enter: route 2 reuses the saved mapping template, so it starts at entity resolution. From step 4 down, the path, the validation and the commit boundary are identical.

Route 1 · UI upload

  • Grower-driven, ad hoc, one file at a time.
  • Handles a first-ever load and any unmapped column.
  • The only route that can resolve new unknown field / variety names, because it can ask.
  • Needed to cold-start a grower, a crop or a geography.

Route 2 · Direct inject

  • Excel drop folder, FMS connection or bulk API, on a schedule.
  • Requires a saved ingest_mapping_template — so it presupposes route 1.
  • Unresolvable names cannot block a batch: they queue to the same worklist for later.
  • This is the route that survives an LFG's real volumes and cadence.

What both share

  • The same staging tables, the same validation rules, the same commit boundary.
  • The same entity_alias resolution, so keys agree across routes.
  • The same batch_id provenance and unit of rollback.
  • One canonical model underneath — figure 3.
FIG 3

The proposed model

Three clusters on one registry. Metrics are rows in metric_definition, not columns — which is what makes the model crop-agnostic and every metric filterable in a WHERE clause instead of in the browser.

FIG 4

What the data is for: the prediction model

The stakeholder experiment design, redrawn. Two lanes meet at one comparison: a live field profile assembled from the user's input, against a benchmark profile built from historical fields that cleared the user's own Productivity Difference threshold and had favourable same-year performance. Note what the fan-out row asks for — PD spread and weighted average PD are zone-level metrics. In figure 3's model those are zone_metric rows, which is what lets this whole row be selected and filtered at the source rather than assembled in the browser.

Successful, defined

A historical field is Successful when it meets both conditions:

  • Productivity Difference ≥ the user-defined threshold, and
  • favourable same-year performance: Returns/ac high, Yield/ac high, Tuber/lb score within the acceptable middle band.

Similarity, not averages

Score the selected field against the benchmark on normalised attributes, because the favourable direction varies:

  • higher drainage may be favourable;
  • lower variability may be favourable;
  • tuber score is best inside a middle band;
  • soil types need categorical similarity, not a higher/lower comparison.

Explain the verdict

A field is Winning when its weighted similarity score is at or above the mean score of the historical Successful fields. The result has to say why:

  • “Matches successful fields on VxC, irrigation and soil suitability.”
  • “Falls below successful benchmarks on drainage score and CEC.”
  • “Closest historical analogues: 4 successful fields with a similar soil mix and variability profile.”
FIG 5

What actually differs between the options

All six give the UI one contract and move the join server-side. They differ in which layer changes, whether PA and FVA sit in the request path, and how far isolation goes.

FIG 6

“Cannot be mixed” is four requirements

Most designs satisfy storage and stop. The recommendation use case in figure 4 lives on the fourth step — so storage isolation alone is not the promise we have made.

FIG 7

Option F: what the gate actually blocks

Raw rows never leave a silo. Only above-threshold cohort statistics cross, through one narrow audited interface — which is what keeps “your data is not mixed” literally true while the prediction model still sees a cohort.

FIG 8

Two phases, no rework between them

Silos first, gate later. Phase 2 reads from exactly what phase 1 builds, so deferring it costs nothing — and retro-fitting silos onto a pooled store is a migration nobody wants to run.
